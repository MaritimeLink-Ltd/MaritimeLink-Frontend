 PART 1 — PRODUCT OVERVIEW AND SCOPE
================================================================================

1.1 WHAT MARITIMELINK IS
------------------------
MaritimeLink is a three-sided marketplace for the maritime industry. It connects

  * Maritime Professionals — seafarers (officers, ratings/crew, catering and
    medical staff) who maintain a verified career profile, a structured maritime
    CV/resume, and a wallet of certificates with expiry tracking;
  * Recruitment Agents — companies that post vacancies, search and shortlist
    candidates, and manage applications end to end;
  * Training Providers (Training Agents) — organisations that publish STCW and
    other maritime courses, schedule sessions, take bookings and get paid out;

and is overseen by a fourth internal role:

  * Platform Administrators — MaritimeLink staff who approve organisations,
    review KYC identity checks, moderate accounts and listings, handle support
    cases and abuse reports, and monitor platform revenue.

1.2 THE THREE APPLICATIONS IN SCOPE
-----------------------------------
The product is delivered as three separate codebases, each with its own Git
repository:

  1. MaritimeLink-Frontend  — React single-page web application.
                              Serves ALL FOUR roles (professional, recruiter,
                              training provider, platform admin).
                              Repo: github.com/MaritimeLink-Ltd/MaritimeLink-Frontend

  2. Maritime-apis          — Node.js/Express + TypeScript REST API and
                              Socket.IO realtime server. The single backend for
                              web and mobile.
                              Repo: github.com/MaritimeLink-Ltd/MaritimeLink-Backend

  3. MaritimeLink-Mobile    — Flutter mobile application (iOS + Android).
                              Professional-facing only; recruiters, training
                              providers and admins use the web app.
                              Repo: github.com/MaritimeLink-Ltd/MaritimeLink-Mobile

All three repositories sit side by side in one parent folder on a developer
machine:

    Maritime/
      |-- Maritime-apis/          (backend)
      |-- MaritimeLink-Frontend/  (web)
      |-- MaritimeLink-Mobile/    (mobile)

1.4 CORE FEATURE SET
--------------------
  Identity and onboarding
    - Multi-step registration wizards, separate per role, resumable at the exact
      step the user abandoned.
    - Email OTP verification for every role.
    - Phone OTP verification (Twilio Verify) for recruiters and training
      providers during signup.
    - Two-stage account assurance:
        Stage 1 = admin approval of the organisation (recruiters/providers)
        Stage 2 = KYC identity verification (document + selfie, AI-assisted OCR)
    - Company auto-discovery: a recruiter enters a company website and the
      system looks up and pre-fills the organisation record.

  Professional features
    - Structured maritime resume: personal details, biometrics, skills, licences
      and endorsements, sea-service log (vessel, IMO, flag, DWT, dates), academic
      education, STCW certificates, medical certificates, travel documents, next
      of kin, referees.
    - Document Wallet: upload certificates by category, OCR extraction of
      names/numbers/dates via Google Gemini, verification status, expiry dates.
    - Automated certificate expiry reminders at 90/60/30/7 days and on expiry.
    - Job discovery, saved jobs, applications with CV and cover letter, and
      application status tracking.
    - Course discovery, booking and Stripe payment; saved courses.
    - Secure, time-limited share links for the profile, the resume and document
      packs.
    - Opt-in public profile page at /in/:slug, server-rendered for SEO.
    - Realtime chat with recruiters, providers and platform support.
    - Free and paid (PRO) membership tiers.

  Recruiter features

    - Candidate search with filters, and AI-assisted matching against a job.
    - Applicant pipeline (applied -> under review -> shortlisted -> interview ->

    - Realtime chat with candidates.

    - Subscription tiers: Free, Flex (per-listing one-off) and Premium (monthly).

  Training provider features
    - Course catalogue with drafts, publishing, capacity and pricing.
    - Sessions (dates, times, location, instructor, seats, enrolment deadline).
    - Attendee approval/rejection, attendance and certificate issue.
    - Demand planning: view aggregate certificate expiries to plan course supply.
    - Revenue and analytics dashboards.
    - Stripe Connect onboarding for payouts; platform commission is 13%.

  Platform administration
    - Approval queues for organisations and KYC submissions, with notes and risk

    - Account moderation: suspend (timed), block, reinstate — with reasons,

    - Member-to-member abuse reports with internal admin note threads.

    - Support case management with priorities, assignment and notes.

1.5 WHAT IS EXPLICITLY NOT IN SCOPE
-----------------------------------
  - There is no separate recruiter or training-provider mobile application.
  - There is no public API for third parties; all endpoints serve first-party

  - There is no data warehouse or BI tool; reporting is computed on demand from

2.2 REQUEST LIFECYCLE (HTTP)
----------------------------
Every API request follows the same path. Understanding it is the fastest way to
understand the backend.

   1  Client attaches `Authorization: Bearer <JWT>` (and, from the web app, an
      `X-Client-IP` header used for audit logging).

   2  Express global middleware, in the exact order registered in src/app.ts:
         app.set('trust proxy', true)      -- correct client IPs behind Render
         GET  /        -> "API is Live"    -- platform health probe
         GET  /health  -> "OK"             -- explicit health probe
         helmet({ crossOriginResourcePolicy: 'cross-origin' })
         cors()                            -- currently permissive, see 16.3
         compression()
         /api/webhooks  MOUNTED BEFORE BODY PARSERS  (Stripe needs the raw body
                        to verify the signature; parsing it first would break
                        signature verification)
         express.json() + express.urlencoded()
         app.disable('x-powered-by')
         /api-docs      -> Swagger UI

   3  Route module matched by prefix (full table in section 6.2).

   4  Auth middleware for that route resolves the caller and attaches req.user.
      Five distinct guards exist — see 2.4.

   5  Controller validates input (Zod schemas in src/validations), calls into
      services, and returns a JSON envelope.

   6  Errors are thrown as AppError or ZodError and handled centrally by
      src/middlewares/errorHandler.ts, which produces a consistent shape and
      only leaks stack traces when NODE_ENV=development.

2.3 REALTIME ARCHITECTURE (Socket.IO)
-------------------------------------
   - The HTTP server created in src/server.ts is shared with Socket.IO.
   - The `io` instance is attached to the Express app (`app.set('io', io)`) so
     controllers can emit without importing the server (avoids circular imports).
   - Handshake authentication: the same JWT, supplied as `socket.handshake.auth
     .token` or an Authorization header. The socket is resolved to a
     Professional, an APPROVED Recruiter, or an Admin; anything else is
     rejected.
   - On connect, each user joins a private room named after their own user id,
     used for targeted notifications.
   - Conversation rooms are joined explicitly via `join_conversation`.
   - Events:
        client -> server : join_conversation, leave_conversation,
                           typing_start, typing_stop, mark_read
        server -> client : user_online, user_offline, user_typing,
                           messages_read, plus notification events emitted by
                           controllers
   - An in-memory Map tracks online users (userId -> set of socket ids). This is
     per-process state; see the scaling note in 2.6.

2.4 AUTHENTICATION AND AUTHORISATION MODEL
------------------------------------------
There is no single users table. Three separate account tables exist —
Professional, Recruiter and Admin — and the JWT carries only `{ id }` (some
tokens also carry `role`). Each guard resolves the id against the table(s) it
cares about:

  +---------------------------+-------------------------------------------------+
  | Middleware                | Accepts / enforces                              |
  +---------------------------+-------------------------------------------------+
  | protect                   | Professional only. Lifts expired suspensions,   |
  | (authMiddleware)          | then rejects restricted accounts with 403.      |
  +---------------------------+-------------------------------------------------+
  | protectRecruiter          | Recruiter only, and status must be APPROVED.    |
  |                           | Also lifts expired suspensions first.           |
  +---------------------------+-------------------------------------------------+
  | protectRecruiterKyc       | Recruiter who is not REJECTED/BLOCKED/SUSPENDED.|
  |                           | Deliberately allows PENDING accounts so a       |
  |                           | recruiter can complete KYC before approval.     |
  +---------------------------+-------------------------------------------------+
  | protectAdmin              | Admin only (SUPER_ADMIN / ADMIN / MODERATOR).   |
  +---------------------------+-------------------------------------------------+
  | protectAdminOrRecruiter   | Admin, or APPROVED Recruiter. Used by the       |
  |                           | shared job and course management routes.        |
  +---------------------------+-------------------------------------------------+
  | protectChat               | Any of the three, tagging req.user.userType so  |
  |                           | conversation and report endpoints can branch.   |
  +---------------------------+-------------------------------------------------+

  Token facts:
    - Algorithm: HS256 (jsonwebtoken default), secret = JWT_SECRET.
    - Lifetime: 7 days for all login tokens.
    - Share links use the same signing key with a short custom TTL (hours), so a
      share link is itself a scoped JWT embedded in a URL.
    - Passwords: bcrypt, cost factor 12.
    - The web client decodes the JWT `exp` claim locally and schedules an
      automatic logout at expiry (src/utils/sessionManager.js).

2.5 ACCOUNT LIFECYCLE STATE MACHINE
-----------------------------------
  Professional
      register -> PENDING -> (email OTP) -> profile steps -> VERIFIED
                     |
                     +-- FLAGGED / SUSPENDED (timed) / BLOCKED  <- admin action
                                    |
                                    +-- automatic reinstatement when
                                        suspendedUntil passes; the account is
                                        restored to statusBeforeSuspension

  Recruiter / Training Provider
      register -> PENDING -> email OTP -> personal info -> phone OTP
               -> company details -> compliance declaration -> submitted
               -> admin decision -> APPROVED | REJECTED
                                       |
                                       +-- FLAGGED / SUSPENDED / BLOCKED

  KYC (both sides, tracked separately from account status)
      not started -> documents uploaded (front/back) -> details submitted
                  -> selfie uploaded -> PENDING -> APPROVED | REJECTED
      A KYC record also stores OCR confidence, mismatch detection and a risk
      level (LOW / MEDIUM / HIGH) to help admins triage.

2.6 DESIGN DECISIONS WORTH KNOWING
----------------------------------
  a) Stateless API, one exception. The API keeps no session state, which is what
     allows Render to restart or scale it freely. The single exception is the
     Socket.IO online-user map. If the API is ever scaled beyond one instance,
     a Socket.IO adapter (Redis) must be added or presence will be wrong.

  b) Prisma with an explicit pg pool. src/config/prisma.ts creates a `pg.Pool`
     and wraps it with `@prisma/adapter-pg` rather than letting Prisma manage
     the connection. This is what makes the Supabase pooled connection
     (pgbouncer, port 6543) work correctly.

  c) Generated Prisma client is committed to the build, not to Git. The client
     is generated into `src/generated/client` (gitignored) and copied into
     `dist/` by the build script.

  d) Money is never trusted from the client. Course prices, commission and
     payouts are recomputed server-side; Stripe Checkout Sessions are created
     by the API and confirmed either by webhook or by an explicit confirm call.

  e) Commission is defined once. `src/config/commission.ts` (backend) is the
     source of truth at 13%; `src/constants/commission.js` (web) mirrors it for
     disclosure copy. These two must always be changed together — they have
     drifted apart in the past.

  f) One support mailbox. `admin@maritimelink.co` is defined once per codebase
     (`src/config/contact.ts`, `src/constants/contact.js`) and used by every
     outbound email and error message.

  g) SEO needs server-rendered HTML. Because the app is a client-rendered SPA,
     public profiles are additionally rendered by a Vercel serverless function
     (`api/profile.js`) that returns real HTML with title, meta description,
     Open Graph/Twitter cards, canonical URL and schema.org JSON-LD, then boots
     the SPA on top for human visitors.

4.7 CODING CONVENTIONS
----------------------
  Backend
    - ESM imports MUST carry the .js extension even in TypeScript source
      (NodeNext resolution). `import { env } from './config/env.js'`.
    - Every async handler is wrapped in catchAsync so errors reach the central
      handler; never call next(err) manually for expected errors — throw
      AppError.
    - Controllers never talk to external APIs directly; that belongs in a
      service.
    - Prettier (single quotes, trailing commas) and ESLint run on commit via
      husky + lint-staged.

  Web
    - Components are .jsx function components; no class components.
    - All network calls go through a module in src/services, which in turn uses
      httpClient — never call fetch directly from a page.
    - Tailwind utility classes; there is no CSS-in-JS.
    - Anything user-visible that duplicates a backend constant (commission,
      support email, document categories) lives in src/constants with a comment
      naming its backend counterpart.

5.5 CASCADE AND DATA-RETENTION BEHAVIOUR
----------------------------------------
  Deleting a Professional cascades to: resume (and every resume child), KYC,
  documents, applications, saved jobs, saved courses, invitations, alerts,
  bookings, conversations and feedback.

  Deleting a Recruiter cascades to: KYC, jobs, courses, conversations and the
  CompanyMember row. The Company itself survives.

  Deliberately NOT cascaded — the audit trail must outlive the account:
      ActivityLog        has no FK at all (actorId is a plain string)
      UserReport         stores reporterEmail/reporterName and
                         reportedEmail/reportedName as denormalised copies
      ReportNote         stores adminEmail as a denormalised copy
      CourseBooking      keeps platformFee and trainerPayout as recorded at the
                         time of sale, so changing the commission rate never
                         rewrites historical payouts

  HOW SCHEMA IS ACTUALLY APPLIED TODAY — read this carefully:
  the backend build script is

      npm run prisma:generate && rm -rf dist && tsc && npx prisma db push && ...

  That is, deployments apply the schema with `prisma db push` (a direct
  schema-sync), NOT with `prisma migrate deploy`. Consequences:
      * The migration folder is not guaranteed to describe production exactly.
      * `db push` will not perform destructive changes without prompting, so a
        rename appears as add-column + orphaned old column.
      * Two features were shipped with hand-written SQL run in the Supabase SQL
        editor instead, documented in
        docs/ACCOUNT_MODERATION_MIGRATION.md and docs/REPORT_NOTES_MIGRATION.md.
        The moderation one MUST be run as two separate statements because
        Postgres cannot use a new enum value in the transaction that added it.
  This is logged as risk R-01 in Part 20 with a recommended remediation.

5.8 BACKUP AND RECOVERY
-----------------------

  plan level held by MaritimeLink Ltd. The client will be upgrading the
  Supabase plan tier, which brings stronger backup retention and Point-in-Time
  Recovery; no further action needed here.

  Manual logical backup (run from a machine with the DIRECT_URL):
      pg_dump "$DIRECT_URL" --no-owner --no-acl -Fc -f maritimelink_$(date +%F).dump

  Recommended: take a manual dump immediately before any release that changes
  the schema, and before running either of the manual SQL migrations in docs/.

6.3 REQUEST AND RESPONSE CONVENTIONS
------------------------------------
  Authentication
      Authorization: Bearer <jwt>
  Optional client header sent by the web app (recorded in ActivityLog)
      X-Client-IP: <ip>
  Content types
      application/json for normal requests
      multipart/form-data for uploads (multer, memory storage)
      application/json RAW for the Stripe webhook only

  Success envelope
      {
        "status": "success",
        "token": "<only on auth endpoints>",
        "data": { ... }
      }

  Error envelope (src/middlewares/errorHandler.ts)
      {
        "status": "error",
        "message": "Human readable message",
        "code": "OPTIONAL_MACHINE_CODE",
        "data": { ...optional context... }
      }
  In development only, `error` and `stack` are added.

  Validation errors (Zod) are converted to HTTP 400 carrying the FIRST issue's
  message, so the UI can show one clear sentence rather than a list.

  Status codes in use
      200 OK, 201 Created
      400 validation / bad request
      401 missing, malformed or expired token; wrong credentials
      403 authenticated but not allowed — includes the account-restriction and
          signup-incomplete cases below
      404 not found (including the catch-all "Can't find <url> on this server!")
      429 rate limited (chat, reports, and Twilio OTP throttling)
      500 unexpected

6.4 MACHINE-READABLE ERROR CODES THE CLIENTS DEPEND ON
------------------------------------------------------
  ACCOUNT_NOT_VERIFIED
      Returned on login when the email OTP was never completed. `data` carries
      { professionalId | recruiterId, email, role? } so the client can jump
      straight to the OTP screen and offer "resend".

  SIGNUP_INCOMPLETE  (see src/utils/signupProgress.ts)
      Returned on login when the account exists and is email-verified but the
      registration wizard was abandoned. `data` carries the id, email, role and
      `registrationStep` so the client resumes at exactly the right page rather
      than showing a dead-end error. This behaviour is covered by seven tests in
      src/__tests__/recruiter.test.ts.

  Account restriction messages
      Suspended, blocked and rejected accounts are rejected with 403 and a
      message produced by `describeRestriction()`, which always names the
      support mailbox. Expired suspensions are lifted automatically on the next
      authenticated request before the check runs.

7.3 TWILIO VERIFY — PHONE OTP
-----------------------------
  Used ONLY for recruiter and training-provider signup. Professionals do not go
  through phone OTP.

  Twilio Verify generates, sends and checks the code, so:
      * no OTP is stored in our database for this path;
      * no purchased Twilio phone number is required — only a Verify Service
        SID (VA...).
  If TWILIO_ACCOUNT_SID + TWILIO_AUTH_TOKEN + TWILIO_VERIFY_SERVICE_SID are not
  all present, the code falls back to a locally generated 6-digit code that is
  logged to the console and emailed. That fallback is what the automated tests
  assume, which is why some of them fail when real Twilio credentials are
  present (see 15.3).

  `sendSMS()` (plain, non-OTP messaging) is the only thing that uses
  TWILIO_PHONE_NUMBER.

7.4 GOOGLE GEMINI — OCR AND COMPANY LOOKUP
------------------------------------------
  Two uses, both in the backend:
    a) Document OCR — `geminiService.analyzeDocument()` extracts name, number,
       issuing country, issue date and expiry date from an uploaded certificate
       or ID, and stores the result in ProfessionalDocument.ocrData with an
       ocrStatus. `validateDocumentType()` checks the upload is the kind of
       document claimed; on API error it deliberately returns true (allow) so a
       Gemini outage cannot block uploads.
    b) Company lookup — `companyService.fetchGeminiCompanyDetails()` turns a
       company website into structured organisation details, which pre-fill the
       recruiter signup form; `compareCompanyDetails()` flags mismatches against
       what the user typed.
  GEMINI_API_KEY is optional in the env schema: without it these features fail
  soft rather than preventing boot.

7.5 EMAIL (SMTP)
----------------
  nodemailer, with the transport configured as `service: 'gmail'` using
  SMTP_USER / SMTP_PASS, and SMTP_FROM as the sender. The transport is verified
  at boot and logs success or failure.

  IMPORTANT CONFIGURATION FACT: because `service: 'gmail'` is used, nodemailer
  supplies Gmail's host and port itself. SMTP_HOST, SMTP_PORT, SMTP_SECURE and
  SMTP_TLS are validated by the env schema but are NOT applied to the
  transport. Pointing the platform at a different mail provider therefore
  requires a code change in src/services/emailService.ts, not just an env
  change. See risk R-06.

  25 email types are implemented. The catalogue lives in
  docs/EMAIL_NOTIFICATION_EVENTS.md and in the exports of emailService:
      Account       OTP verification, password reset, phone OTP,

      KYC           submitted, approved/rejected, resubmission requested
      Jobs          application submitted (to both sides), invited to apply,
                    application status changed, job published
      Training      booking confirmed (to both sides), booking cancelled,
                    course published
      Money         payment success / failure
      Documents     expiry reminder, expiry digest, secure link shared
      Support       support case created / updated
      Moderation    report acknowledged, report resolved

  All email HTML is produced by src/services/emailLayout.ts (brand shell,

                       documents today, (a) is the more likely explanation.
                       RECOMMENDATION: check each bucket's Policies tab in the
                       Supabase dashboard; for the two KYC buckets and the
                       ID-passport buckets in particular, replace any public-read
                       policy with authenticated, time-limited access via

9.7 SCHEDULED WORK (CRON)
-------------------------
    One scheduled job exists: the daily document-expiry reminder.

        Production   node dist/scripts/send-expiry-reminders.js
                     (npm run job:expiry-reminders:prod)
        Development  npm run job:expiry-reminders
        Dry run      npm run job:expiry-reminders -- --dry-run
        Single user  npm run job:expiry-reminders -- --only user@example.com

    It is designed to be triggered by an EXTERNAL scheduler (Render Cron Job,
    GitHub Actions, or a cloud scheduler) rather than in-process, so that
    exactly one instance runs it. It is safe to run more than once a day:
    reminder state is written only after successful delivery, so a repeat run
    sends nothing and a failed run retries. A non-zero exit code is returned if
    any email failed, so the scheduler surfaces problems.

    CONFIRMED: currently runs daily at 08:00 UTC. The client intends to move
    this to a WEEKLY cadence instead of daily. The specific scheduler logic itself does not need to change — it is milestone-based (90/60/30/7
    days and on expiry, see 4.2) and safe to run at any cadence, since it only

12.1 DEPLOYMENT MODEL
---------------------
    Backend  -> Render, deployed from the `master` branch of
                MaritimeLink-Ltd/MaritimeLink-Backend
    Web      -> Vercel, deployed from the `main` branch of
                MaritimeLink-Ltd/MaritimeLink-Frontend; every pull request also

12.2 DEPLOYING THE BACKEND
--------------------------
    1  Merge to `main`.
    2  Render builds:  npm ci && npm run build
       (this runs `prisma db push`, so the schema is synced as part of the
       deploy — see the warning in 11.1 and risk R-01)
    3  Render starts:  npm start   ->  node dist/server.js
    4  Health check `/health` must return 200 before traffic is switched.
    5  Verify manually:
         curl -s https://<api-host>/health
         curl -s https://<api-host>/ | head
         open https://<api-host>/api-docs
    6  Watch the Render log for the boot sequence in 10.3. In particular confirm
       "🗄️  Database connected successfully" and "✅ SMTP Server is ready".

    Zero-downtime: Render performs a rolling replace once the health check
    passes. Because the API is stateless apart from Socket.IO presence, active
    WebSocket clients will reconnect automatically after a deploy.

12.3 DEPLOYING THE WEB APP
--------------------------
    1  Confirm all VITE_ variables are set for the Production environment in
       Vercel (they are inlined at build time — a missing one ships a broken
       bundle, not a runtime error).
    2  Merge to `main`; Vercel builds `npm run build` and publishes `dist`.
    3  Confirm the two serverless functions deployed:
         https://www.maritimelink.co/in/<a-known-public-slug>
             -> view source; it must contain a real <title>, meta description
                and JSON-LD, not the empty SPA shell
         https://www.maritimelink.co/sitemap-profiles.xml
             -> valid XML listing public profiles
    4  Spot check one route from each role area (see the smoke test in 12.6).

12.4 DEPLOYING THE MOBILE APP
-----------------------------
    1  Bump `version:` in pubspec.yaml (always increment the build number).
    2  Confirm the compiled API base URL is correct (see 8.4 — there is a known
       discrepancy to resolve first).
    3  Build with the release commands in 11.3.
    4  Upload: App Store Connect (TestFlight -> review) and Play Console
       (internal testing -> production).
    5  Because configuration is compiled in, a wrong API URL cannot be fixed
       without a new release. Verify against a staging API before submitting.

12.5 DATABASE CHANGES DURING A DEPLOY
-------------------------------------
    Additive changes (new nullable column, new table, new index) are applied
    automatically by `prisma db push` during the backend build.

    Anything that could lose data — dropping or renaming a column, changing a
    type, adding an enum value that is used in the same transaction — must be
    done deliberately:
        1  Take a manual dump (see 5.8).
        2  Write the SQL by hand, following the pattern in
           docs/ACCOUNT_MODERATION_MIGRATION.md (additive, idempotent, split
           into steps where Postgres requires it).
        3  Run it in the Supabase SQL editor against production.
        4  Update prisma/schema.prisma to match.
        5  Deploy the code that depends on it.
    Adding an enum VALUE and USING it must be two separate statements/steps —
    Postgres refuses to use a new enum value inside the transaction that
    created it, and the Supabase SQL editor wraps each submission in a
    transaction.

12.7 ROLLBACK
-------------
    Web       Vercel -> Deployments -> pick the last good deployment ->
              "Promote to Production". Instant.
    Backend   Render -> Deploys -> "Rollback" to the previous successful deploy.
              CAUTION: a rollback of code does NOT roll back schema changes
              applied by `prisma db push` on the way in. If the failed deploy
              changed the schema, restore from the pre-deploy dump or apply a
              compensating SQL change.
    Mobile    Play Console supports halting a staged rollout; the App Store
              requires submitting a new build. Plan mobile releases with a
              staged rollout percentage.

12.8 SECRET ROTATION PROCEDURE
------------------------------
    JWT_SECRET                Rotating logs out every user AND invalidates every
                              outstanding secure share link. Do it during a
                              maintenance window and tell users.
    STRIPE_SECRET_KEY         Roll in the Stripe dashboard, update Render, redeploy.
    STRIPE_WEBHOOK_SECRET     Only changes if the webhook endpoint is recreated.
    SUPABASE_SERVICE_ROLE_KEY Rotate in Supabase, update Render, redeploy.
                              Highest-impact secret in the system.
    SMTP_PASS                 Regenerate the Gmail app password.
    TWILIO_AUTH_TOKEN         Roll in the Twilio console.
    GEMINI_API_KEY            Regenerate in Google AI Studio / Cloud console.
    In all cases: update the value in Render (or Vercel) FIRST, then redeploy,
    then revoke the old credential — not the other way round.

13.1 SUPABASE — DATABASE

13.2 SUPABASE — STORAGE
-----------------------
    Create these eight buckets (or set the matching env vars to your own names):
        professional-ids
        recruiter-ids
        professional-kyc-documents
        professional-kyc-selfies
        recruiter-kyc-docs
        recruiter-kyc-selfies
        document-wallet
        resumes
    The API uploads with the service-role key and returns each object's public
    URL, so the app expects the URL to be readable by the browser. CONFIRMED
    by the client: all eight buckets are set to PRIVATE at the bucket level.
    As set out in 9.5, this needs reconciling with the code, which calls
    getPublicUrl() (the public-bucket API) on every upload — either a
    public-read storage policy is layered on top of these "private" buckets
    (making them effectively public despite the toggle), or uploaded files are
    not actually loading for users. Resolve which is true before relying on
    "private" as a real security boundary for the KYC document and selfie
    buckets. See risk R-08.

13.3 STRIPE
-----------
    1  Dashboard -> Developers -> API keys: copy the publishable and secret keys.
    2  Products:
       a) Professional membership — create RECURRING prices as Stripe products.
          The API reads the catalogue live, so whatever active recurring
          products exist appear in the app. Two naming rules are enforced in
          code: products named "course" and products whose name contains
          "recruiter" are excluded from the professional membership list. Name
          paid professional plans with "Maritime " as a prefix if you want the
          app to strip it for display.
       b) Recruiter plans — create exactly two prices and put their ids in env:
             Flex Recruiter     GBP  99.90  one-time

14.3 TROUBLESHOOTING RUNBOOK
----------------------------
  SYMPTOM: API will not start; log shows "❌ Invalid environment variables"
    CAUSE:  a required variable is missing or malformed (Zod).
    FIX:    the printed object names the exact field. Add it in Render ->
            Environment and redeploy. Common culprits: DATABASE_URL not a valid
            URL, SMTP_FROM not a valid email, a missing STRIPE_RECRUITER_*_PRICE_ID.

  SYMPTOM: "The user belonging to this token no longer exists" (401)
    CAUSE:  the account was deleted, or the token was signed with a different
            JWT_SECRET (e.g. a token from staging used against production).
    FIX:    sign in again. If widespread, check whether JWT_SECRET changed.

  SYMPTOM: recruiters report "Your account is not approved yet" (403)
    CAUSE:  Recruiter.status is not APPROVED. protectRecruiter enforces this.
    FIX:    admin approves at /admin/accounts, or investigate why the Stage 1
            decision was not recorded.

  SYMPTOM: a user says they are locked out with a "contact support" message
    CAUSE:  the account is SUSPENDED, BLOCKED or REJECTED.
    FIX:    /admin/accounts/:id -> moderation panel -> reinstate. Expired
            timed suspensions lift themselves on the next login attempt; if one
            has not, check `suspendedUntil`.

  SYMPTOM: user completes signup but is bounced back to a wizard step
    CAUSE:  correct behaviour — the SIGNUP_INCOMPLETE 403. Their
            `registrationStep` has not advanced.
    FIX:    have them finish the step named in the response, or inspect the
            account row to see which field is still null.

  SYMPTOM: phone OTP never arrives during recruiter signup
    CHECK:  1) Are all three TWILIO_* Verify variables set? If not, the code was
               emailed instead and logged to the console.
            2) Twilio console -> Verify -> Logs for the attempt.
            3) Geographic permissions for that country.
            4) A 429 from us means Twilio's own rate limit (codes 60203/60212/
               60410) — the user must wait.

  SYMPTOM: no emails are being delivered
    CHECK:  boot log for the SMTP verification result; Gmail app password
            validity; Gmail sending limits; the recipient's spam folder; and
            whether SPF/DKIM are configured for the sending domain.

  SYMPTOM: email links point at localhost
    CAUSE:  FRONTEND_URL is wrong in the API environment.
    FIX:    set it to the production web origin and redeploy.

  SYMPTOM: a Stripe payment succeeded but the booking/membership did not update
    CHECK:  Stripe -> Webhooks -> delivery attempts for that event. A 400
            usually means signature verification failed, which almost always
            means STRIPE_WEBHOOK_SECRET is wrong OR a body parser was mounted
            before the webhook route (the raw body must reach the handler
            unparsed).
    FIX:    correct the secret and use "Resend" on the failed events. The
            explicit confirm endpoints (POST .../membership/confirm,
            POST .../course-bookings/:id/confirm) are the manual fallback.

  SYMPTOM: document OCR is not extracting fields
    CHECK:  GEMINI_API_KEY present; Gemini quota; the log line
            "❌ Gemini OCR Error". Uploads still succeed with ocrStatus FAILED;
            the user can enter the fields manually.

  SYMPTOM: chat messages do not arrive in realtime (but appear after refresh)
    CHECK:  the WebSocket connection in the browser network tab; whether the
            Render service supports/has WebSockets enabled; whether the token
            was accepted by the handshake (a Recruiter must be APPROVED to
            connect); and whether the client called `join_conversation`.

  SYMPTOM: uploaded file URLs 404 or are refused
    CHECK:  the bucket exists and its name matches the env var; the Supabase
            service-role key is valid; the bucket's public/private policy.

  SYMPTOM: the public profile page has no metadata when shared on LinkedIn
    CHECK:  the Vercel rewrite for /in/:slug is present and the
            api/profile.js function deployed; the API_BASE_URL env var is set
            on Vercel; and the profile actually has publicProfileEnabled.

  SYMPTOM: first request after a quiet period is very slow
    CAUSE:  Render free/starter tier cold start.
    FIX:    upgrade the plan, or keep the service warm with an external uptime
            monitor hitting /health.

14.4 DATA OPERATIONS
--------------------
  Find and inspect an account
      Admin console -> /admin/accounts, or GET /api/admin/accounts/:id.
  Moderate an account
      POST /api/admin/accounts/:id/suspend | /block | /reinstate. Suspension

      holding denormalised name/email for audit. Assess whether those copies
      must also be redacted for a given request, and remove the corresponding
      files from Supabase Storage manually — object deletion is NOT cascaded by
      the database.

15.5 STRUCTURAL FINDINGS ABOUT THE BACKEND TEST SUITE
-----------------------------------------------------
  These are the most important things a new maintainer must know:

  F-1  THE TESTS RUN AGAINST THE REAL DATABASE. There is no separate test
       database, no transactional rollback and no fixture reset. Suites create
       real rows and clean up after themselves in `afterAll`. Running
       `npm test` with production credentials in .env would write to production.
       RECOMMENDATION: introduce a dedicated test database URL and make the
       Jest setup refuse to run unless it is set.

  F-2  THE TESTS CALL REAL EXTERNAL SERVICES. Gemini and Twilio are invoked for
       real, which is why results vary between runs, why the suite takes ~3
       minutes, and why it consumes API quota and can send real SMS/email.
       Email is the exception — `src/testing/mockEmailService.ts` provides a
       complete mock that suites use.
       RECOMMENDATION: mock geminiService and smsService the same way
       emailService is already mocked.

  F-3  JEST REPORTS "A worker process has failed to exit gracefully". Something
       (most likely the pg pool, the nodemailer transport or a Socket.IO
       handle) is not closed in teardown. Harmless today; it will mask real
       leaks later. Diagnose with `--detectOpenHandles`.

  F-4  Suite runtime is long (recruiterSubscriptionGating 92 s, recruiter 184 s)
       because of the live network calls. Mocking F-2 would bring the suite
       under a minute and make it CI-viable.

16.1 WHAT IS IMPLEMENTED
------------------------
  Authentication      bcrypt (cost 12) password hashing; HS256 JWTs with a
                      7-day lifetime; OTP email verification for every role;
                      phone OTP (Twilio Verify) for organisations; password
                      reset via single-use tokens with expiry.
  Authorisation       Five distinct server-side guards (2.4). Every protected
                      route names its guard explicitly at the route definition.
  Account safety      Suspension (timed, auto-lifting), blocking, rejection,
                      and flagging, all enforced inside the auth guards so a
                      restricted account cannot use ANY protected endpoint, not
                      just the UI it was blocked from.
  Identity assurance  Two-stage: organisation approval + KYC document and selfie
                      with OCR cross-checking, mismatch detection, confidence
                      scoring and a risk level for triage.
  Transport/headers   helmet; x-powered-by disabled; HTTPS everywhere via Vercel
                      and Render; `trust proxy` set so client IPs are correct.
  Input validation    Zod schemas on request bodies; ZodError converted to a
                      clean 400.
  Payments            No card data ever touches MaritimeLink servers — Stripe
                      Checkout is used. Webhooks are signature-verified against
                      the raw body.
  Secrets             Server-only. Supabase service-role key, Stripe secret key
                      and Twilio token exist only in the backend environment.
                      `.env` is gitignored in all three repositories (verified).
  Audit               ActivityLog records actor, action, target, IP, user agent
                      and outcome. Report and note records denormalise author
                      identity so the trail survives account deletion.
  Abuse handling      Member-to-member reporting with rate limiting, admin
                      review workflow and notification of both parties.
  Rate limiting       Chat routes and report submission; Twilio enforces OTP
                      throttling.
  Share links         Time-limited JWTs; robots.txt excludes shared paths from
                      indexing; public profiles are strictly opt-in
                      (publicProfileEnabled defaults to false).
  Client session      The web app decodes `exp` and forces logout at expiry,
                      and distinguishes an expired token (log out) from a
                      role-forbidden 401 (do not log out).
  Legal framework     Nine policy documents are published in the app: Terms,
                      Privacy, Cookie, Acceptable Use, Recruiter Terms, Training
                      Provider Terms, Professional User Terms, Data Retention &
                      Secure Deletion, and Information Security & Vulnerability
                      Disclosure. Terms and Privacy are public; the rest are
                      members-only by deliberate design (LegalRouteGuard).

16.2 PERSONAL DATA HELD
-----------------------
  MaritimeLink processes a significant amount of personal and special-category-
  adjacent data. Anyone maintaining this system must know where it lives:
      Identity          name, DOB, nationality/issue country, government ID
                        type and number, ID document images (front/back),
                        selfie images
      Contact           email, phone, full postal address, next-of-kin details
      Biometric-ish     height, weight, BMI, eye colour, clothing and shoe size
                        (used for uniform/PPE sizing in maritime employment)
      Medical-adjacent  medical certificates and their numbers/expiries
      Employment        full career history, vessels served, referees
      Financial         Stripe customer/subscription identifiers (no card data)
      Behavioural       activity logs including IP address and user agent
  Storage locations: Supabase Postgres (structured data) and Supabase Storage
  (all document and selfie images).

16.3 KNOWN SECURITY WEAKNESSES (full detail in Part 20's risk register)
-----------------------------------------------------------------------
  S-1  CORS is fully permissive. `app.use(cors())` with no options allows any
       origin. Socket.IO is configured with `origin: '*'` and the code comment
       says "Adjust for production". Because the API is token-authenticated
       (not cookie-authenticated) this is not immediately exploitable for CSRF,
       but it removes a defence layer and allows any site to call the API with a
       token it has obtained.
       FIX: an explicit allow-list built from FRONTEND_URL.

  S-2  Socket room membership is not verified. `join_conversation` joins any
       room id the client asks for; the source comment states "In a real app,
       verify user belongs to conversation first". A user who learns a
       conversation id could receive that conversation's realtime events.
       Message HISTORY is still protected by the REST endpoints.
       FIX: check participation against the Conversation row before joining.

  S-3  No file size or MIME allow-list on uploads. multer uses memory storage
       with no `limits`, so a large upload is buffered in the API's heap.
       FIX: add `limits: { fileSize: ... }` and a MIME filter.

  S-4  No rate limiting on authentication endpoints. Login, register and
       forgot-password can be called without application-level throttling.
       FIX: apply express-rate-limit to the auth routes.

  S-5  SQL query logging in production (`log: ['query']`). Query text with
       parameter values ends up in the Render log stream.
       FIX: make the log level environment-dependent.

  S-6  Storage objects are served via getPublicUrl(), the public-bucket API,
       even though the client confirms all eight buckets are toggled PRIVATE.
       That combination only works if a public-read storage policy is layered
       on top of the private toggle — meaning the buckets are very likely
       public-readable in practice regardless of the private setting. Signed
       URLs (createSignedUrl(), time-limited) would be a real fix for the KYC
       document and selfie buckets specifically. See 9.5 and R-08.

  S-7  A seeded SUPER_ADMIN with a published password exists in the codebase
       (prisma/seed.ts). It must not exist in production.

  S-8  `validateDocumentType()` defaults to ALLOW when Gemini errors. This is a
       deliberate availability trade-off, but it means a Gemini outage disables
       that check silently.

   Personal -> My Jobs tracks every application. Statuses you will see:
     Applied -> Under review -> Shortlisted -> Interview -> Offer -> Hired
     or Rejected (with a reason) / Withdrawn (by you)
   You are emailed whenever the status changes. You can withdraw an application
   at any time.

   Recruiters can also invite you to apply to a specific job — those invitations
   arrive by email and appear in your dashboard.

 TRAINING COURSES
   Personal -> Training. Browse courses, open one to see the curriculum,
   requirements, certification provided, duration and price, then pick a session
   (date, time, location, instructor, seats remaining).

   Book and pay by card through Stripe. You will receive a booking confirmation
   email, and the training provider is notified at the same time. Track your
   bookings under Training; you can cancel from the booking detail screen
   subject to the provider's terms.

 MESSAGES
   Personal -> Chats. Message recruiters and training providers, and contact
   MaritimeLink support. Messages are delivered in real time; you can see when
   the other person is typing and when your message has been read. You are also
   emailed if a message arrives while you are away.

 SHARING YOUR PROFILE
   Three separate options, all under your control:
     Public profile     Turn it on in your profile settings to get a public page
                        at maritimelink.co/in/your-name. Search engines can find
                        it. Off by default.
     Secure profile link  Generates a private, time-limited link to your full
                        profile. Anyone with the link can view it until it
                        expires — do not post it publicly.
     Document pack link Same idea, for a chosen set of wallet documents.
   Secure links are excluded from search engines. You choose how many hours they
   remain valid.

 MEMBERSHIP
   Free includes: dashboard, public profile, resume builder, document wallet,
   unlimited job applications, course browsing and booking, recruiter messaging,
   application tracking and certificate expiry reminders.
   Paid (PRO) adds: secure profile sharing, secure resume sharing and PDF
   download, secure document-pack sharing and download, priority visibility in
   recruiter search, priority candidate matching, and priority support.
   Manage or cancel under Personal -> Profile -> Manage Subscription.

 ACCOUNT AND PRIVACY
   Change your password, control your availability status ("available for work"
   or not), control your public profile visibility, report another member,
   contact support, and delete your account (which removes your profile, resume,
   documents and applications) — all from Personal -> Profile.

 17.3 TRAINING PROVIDER (TRAINING AGENT)

 REGISTERING
   The same six-step organisation signup as a recruitment agent, started from

 GETTING PAID — SET THIS UP FIRST

 MANAGING BOOKINGS AND ATTENDANCE

 17.4 PLATFORM ADMINISTRATOR (MARITIMELINK STAFF)
--------------------------------------------------------------------------------

 SIGNING IN
   /admin/login. Roles are SUPER_ADMIN, ADMIN and MODERATOR.

 THE DAILY QUEUES (admin dashboard -> Queues)
   Pending organisation approvals, pending KYC submissions, open abuse reports,
   unassigned support cases and flagged listings. These are the work queues; the
   dashboard also shows platform statistics and revenue at a glance.

 APPROVING ORGANISATIONS  (Accounts / Compliance)
   Open a pending recruiter or training provider. Review who they say they are,
   what the automated company lookup found, and any mismatch flags. Approve or
   reject with a reason — the applicant is emailed either way. Add internal
   notes for colleagues; notes are never shown to the member.

 REVIEWING KYC  (Compliance)
   Each submission shows the ID document (front and back), the selfie, the
   details the user entered, what OCR read from the document, an OCR confidence
   score, any detected mismatch, and a risk level (Low / Medium / High).
   Approve, reject, or set it back to pending to request a resubmission — each
   outcome sends the appropriate email. Attach notes to record your reasoning.

 MODERATING ACCOUNTS
   From any account profile you can:
     Suspend    optionally until a specific date, with a reason. The user is
                emailed and cannot use the platform. When the date passes, the
                suspension lifts itself automatically and the account returns to
                its previous status.
     Block      indefinite. Requires manual reinstatement.
     Reinstate  restores the account to the status it held before moderation.
   Every action is recorded in the activity log.

 HANDLING ABUSE REPORTS  (Reports)
   Reports are member-to-member complaints, distinct from support cases. Each
   has a reference, both parties' details, a reason, the member's description
   and optionally the conversation it relates to. Work a report by moving it
   Pending -> Under review -> Actioned or Dismissed, recording the action taken
   (none, warning issued, account suspended, account blocked) and a resolution
   note. Multiple admins can add internal notes to the same report. The reporter
   is emailed on acknowledgement and again on resolution.

 SUPPORT CASES  (Operations)
   Cases raised by members, each with a human-readable case ID, category,
   priority and status (Open / Resolved / Closed). Assign a case to yourself,
   add internal notes (staff only) or replies (visible to the member), and
   resolve.

 MARKETPLACE OVERSIGHT
   Two views:
     Internal   MaritimeLink's own first-party jobs and courses, which admins
                can create and manage directly.
     Oversight  every job and course posted by recruiters and providers, with
                the ability to flag, unflag or remove a listing, and to drill
                into a specific organisation's listings.

 COMPANIES
   The organisation register. Review claimed and verified companies, edit
   details, manage team members, and merge duplicate company records.

 OPERATIONS AND AUDIT
   Activity log: every significant action with actor, target, IP address, user
   agent, outcome and timestamp — searchable and drillable.
   System statistics, system alerts and manual-action review live alongside it.

 FINANCE
   Revenue overview across memberships, recruiter subscriptions and course
   commission; transaction history; and trainer payout management including
   initiating a provider's Stripe onboarding on their behalf.

 BULK OPERATIONS
   Jobs can be bulk-uploaded by CSV; download the sample file from the admin
   jobs screen to get the exact expected columns.

 18.4 FREQUENTLY ASKED QUESTIONS (support-desk crib sheet)
--------------------------------------------------------------------------------
   Q  "I didn't get my verification code."
   A  Resend from the OTP screen; check spam. For recruiters, the PHONE code
      comes from Twilio — if Twilio is misconfigured the code is emailed
      instead. Check the Twilio Verify log.

   Q  "I signed in and it sent me back to a signup page."
   A  Correct behaviour. Their registration was never finished; the platform
      resumes them at the exact step. Ask which step they see.

   Q  "My account says contact support."
   A  It is suspended, blocked or rejected. Check the moderation panel on the
      account. Timed suspensions lift themselves.

   Q  "I paid but nothing happened."
   A  Check Stripe for the payment, then check the webhook delivered. If the
      webhook failed, resend it from the Stripe dashboard.

   Q  "My certificate details were read wrong."
   A  OCR is assistive only. Every field is editable; ask them to correct it.

   Q  "Recruiters can't see me."
   A  Check: is the profile complete, is availability set to available, is the
      account verified, and (for search prominence) is the membership free or
      paid?

   Q  "How do I stop my profile appearing on Google?"
   A  Turn off the public profile toggle in profile settings. It is off by
      default; only opted-in profiles are published and included in the sitemap.

   Q  "Can I get all my data?"
   A  They can download their resume as a PDF and their document pack. There is
      no one-click full export today; a subject access request must be handled
      manually.

   Q  "I want my account deleted."
   A  Self-service deletion exists in profile settings and cascades their
      personal data. Note that uploaded files in storage and audit records need
      separate handling — see 14.4.

19.4 MENTAL MODELS THAT PREVENT MISTAKES
----------------------------------------
    * "Recruiter" in the database means recruitment agent OR training provider.
      The `role` column separates them. Half the confusion in this codebase
      comes from forgetting that.
    * There is no `users` table. Three account tables, one JWT format, five
      guards.
    * The API is the only thing that may touch secrets. If you find yourself
      wanting a secret in the web or mobile app, the design is wrong.
    * Emails are side effects that must never fail a transaction — always go
      through eventNotificationService/safeNotify.
    * Money constants are duplicated across repos ON PURPOSE, with comments
      pointing at each other. Change them together or the product lies to users.
    * `npm run build` on the backend changes the database. Say it out loud
      before you run it.

20.3 RISK REGISTER
------------------
  Severity: H = high, M = medium, L = low

  R-01  H  SCHEMA IS APPLIED WITH `prisma db push` AT BUILD TIME
           Production schema changes happen as a side effect of deploying, the
           migrations folder is not guaranteed to describe production, and two
           features were applied by hand-written SQL. There is no reliable way
           to reproduce the production schema from source, and no rollback path
           for a schema change.
           MITIGATION: move to `prisma migrate deploy`; baseline the current
           production schema as an initial migration; remove `prisma db push`
           from the build script; take a dump before every schema-affecting
           release.

  R-02  H  SOCKET.IO ROOM MEMBERSHIP IS NOT VERIFIED
           `join_conversation` joins any room id supplied by the client. An
           authenticated user who obtains a conversation id could receive that
           conversation's live events.
           MITIGATION: verify participation against the Conversation row inside
           the handler before joining. Small, well-contained change.

  R-03  M  SQL QUERY LOGGING IS ENABLED IN PRODUCTION
           `log: ['query']` writes every statement to the Render log stream,
           adding overhead, cost and potential exposure of data in logs.
           MITIGATION: make the log array conditional on NODE_ENV.

  R-04  M  NO RATE LIMITING ON AUTHENTICATION ENDPOINTS
           Login, register and forgot-password are unthrottled at the
           application layer, enabling credential stuffing and email
           enumeration/abuse.
           MITIGATION: apply express-rate-limit (already a dependency) to the
           auth routes of all four roles.

  R-05  M  NO UPLOAD SIZE OR TYPE LIMITS
           multer uses memory storage with no `limits` and no MIME filter, so a
           large or hostile upload is buffered in the API's heap.
           MITIGATION: add fileSize limits and an allow-list of MIME types.

  R-06  M  PERMISSIVE CORS AND SOCKET ORIGIN
           `cors()` with no options and Socket.IO `origin: '*'`. The code itself
           carries the note "Adjust for production".
           MITIGATION: allow-list built from FRONTEND_URL.

  R-07  M  SINGLE API INSTANCE ASSUMPTION
           Socket.IO presence is held in an in-process Map. Scaling the Render
           service beyond one instance will silently break online status and
           room delivery.
           MITIGATION: add the Socket.IO Redis adapter before scaling out.

  R-08  H  STORAGE OBJECT EXPOSURE — BUCKET "PRIVATE" SETTING LIKELY NOT
           ENFORCED IN PRACTICE
           The client confirms all eight Supabase buckets are set to PRIVATE.
           But every upload path in the code (storageService.uploadToSupabase)
           calls getPublicUrl(), which is Supabase's API for PUBLIC buckets —
           it does not generate a signed/authenticated URL. For that call to
           produce a URL that actually works for end users (which it visibly
           does — profile photos, document wallet files and KYC images render
           in the app today), a storage RLS policy almost certainly grants
           anonymous SELECT on these "private" buckets, which defeats the
           private toggle. In practice, this means identity documents and
           selfies are very likely reachable by anyone who obtains the URL,
           not protected as the private setting implies.
           MITIGATION: in the Supabase dashboard, open each bucket's Policies
           tab and check for a public/anon SELECT policy. For the KYC document
           and selfie buckets especially, remove the public-read policy and
           switch the API to createSignedUrl() (short-lived, authenticated)
           instead of getPublicUrl(). This is now the single highest-priority
           item in this risk register — raised from Medium to High because the
           client's confirmed "private" setting does not match what the code
           actually does.

  R-09  M  NO ERROR TRACKING OR UPTIME MONITORING
           Failures are only visible by reading Render logs. Nobody is paged.
           MITIGATION: add Sentry (or equivalent) to the API and the web app,
           and an external uptime monitor on /health.

  R-10  M  NO CI PIPELINE
           Nothing prevents a commit that fails type-checking, linting or tests
           from reaching production. The only gate is a local pre-commit hook on
           staged files.
           MITIGATION: the three-job GitHub Actions workflow described in 11.6.

  R-11  L  SEEDED ADMIN WITH A PUBLISHED PASSWORD
           admin@maritime.com / Password123! is in the repository.
           MITIGATION: confirm it does not exist in production; keep the seed
           for development only.

  R-12  L  TESTS RUN AGAINST A REAL DATABASE AND REAL THIRD PARTIES
           Running `npm test` with the wrong .env would write to production and
           consume/charge external quota.
           MITIGATION: a dedicated TEST_DATABASE_URL that the Jest setup
           requires, plus mocks for Gemini and Twilio.

  R-13  L  KEY-PERSON DEPENDENCY
           Much of the operational knowledge (which Render service is live, how
           the cron is scheduled, where the signing keys are) lives with the
           original developer.

 APPENDIX C — GLOSSARY
================================================================================
 Application status   The stage of a job application: Applied, Under review,
                      Shortlisted, Interview, Offer, Hired, Rejected, Withdrawn.
 Booking              A professional's reservation of a course session,
                      including its payment state.
 Company              An organisation record, keyed by web domain, that
                      recruiters and training providers belong to.
 CourseBooking        The database record of a paid course reservation. Stores
                      the platform fee and trainer payout as at the time of sale.
 CourseSession        A specific scheduled delivery of a course: dates, times,
                      location, instructor and seats.
 Document Wallet      A professional's store of uploaded certificate files,
                      organised by category, with OCR-extracted metadata and
                      expiry tracking.
 DWT                  Deadweight tonnage — a vessel size measure recorded in the
                      sea-service log.
 Flex listing         A one-off paid promotion of a single job listing for 30
                      days (GBP 99.90).
 IMO number           A vessel's permanent International Maritime Organization
                      identification number.
 KYC                  Know Your Customer — identity verification using a
                      government document plus a selfie.
 Milestone (expiry)   One of 90, 60, 30 or 7 days before expiry, or expiry
                      itself. Each triggers at most one reminder.
 Moderation           Admin action on an account: suspend (timed), block
                      (indefinite) or reinstate.
 OCR                  Optical Character Recognition — here, Gemini reading a
                      certificate or ID and extracting structured fields.
 Professional         A seafarer user of the platform.
 Public profile       An opt-in, search-engine-indexable page at /in/:slug.
 Ratings              Non-officer crew ranks (deck or engine).
 Recruiter            In the DATABASE, any organisation user — either a
                      RECRUITMENT_AGENT or a TRAINING_AGENT. In the UI,
                      "recruiter" means only the former.
 Report               A member-to-member abuse complaint, distinct from a
                      support case.
 Resume snapshot      A frozen copy of the resume as submitted with a job
                      application, so later edits do not rewrite history.
 Sea service          The record of a professional's contracts at sea: vessel,
                      rank, dates and vessel characteristics.
 Secure share link    A time-limited JWT embedded in a URL that grants read
                      access to a profile, resume or document pack.
 STCW                 Standards of Training, Certification and Watchkeeping —
                      the IMO convention governing mandatory seafarer
                      certification.
 Stage 1 / Stage 2    Stage 1 is admin approval of an organisation; Stage 2 is
                      KYC identity verification of the individual.
 Support case         A help request raised by a member, with a case ID,
                      priority, assignment and notes.
 Tier                 The commercial plan on an account: FREE/PRO for
                      professionals, FREE/PREMIUM for recruiters and providers.
 Training Agent       The database role name for a Training Provider.
